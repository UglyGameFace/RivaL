# RivaL multi-venue forecast/learning core

**Status: foundational domain layer, not a live perpetuals prediction bot.**
The existing Discord sports interface and deployment are intentionally unchanged.
This uses the existing PostgreSQL connection via `RelationalHotStore` when
initialized, and only adds isolated `perp_predictions` and `perp_source_skill`
tables. The ledger is not yet wired into runtime startup.

## Ten source candidates

Hyperliquid, dYdX, Lighter, Deribit, Binance Futures, OKX, Bitget, Gate
Futures, KuCoin Futures and Phemex. **Kraken is excluded.** All candidates
require confirmation of public read-only access, regional eligibility, symbol
and contract semantics, rate limits and uptime from Discloud before enabling.
See GitHub issue #6 for each venue's official documentation and constraints.

## Source fusion

`SourceForecast` requires a venue-specific, point-in-time **forecast
probability** generated by a separately validated upstream prediction model.
A raw price, agreement statistic, or funding rate is *not* a probability.
`fuse_forecasts` refuses instrument/horizon mismatches, rejects future/stale
or low-quality observations, deduplicates mirrored upstreams, requires at
least three independent source origins, caps any venue at 40%, and shifts
disagreeing forecasts toward 50%. It never fabricates unavailable observations
or averages prices across venues. The resulting agreement is **not** measured
prediction accuracy, and no claim of predictive edge is made here.

## Delayed learning

`PredictionLedger` saves predictions and all contributing probabilities
immutably, using the same relational store as RivaL's production application.
It is safe to retry record/settle without double-counting. Settlement
requires a real market observation from the original reference venue,
timestamped at the forecast's due time within two minutes. Until then,
the prediction cannot update source skill. Each settled outcome updates a
per-asset, quote, horizon and upstream-origin Brier score, including a
discounted recent score. Subsequent fusions favor better historical scorers.
`performance()` reports results only from settled observations.

This is **online reliability-weight adaptation**, not autonomous model
training. To implement the requested continually learning system, RivaL
still needs: 10 permitted live adapters, historical backfill, normalization,
features, leakage-proof labeling, model training/calibration, proper
walk-forward tests, controlled challenger/champion promotion, scheduled
outcome settlement, source-health gating, Discord presentation and Discloud
validation. Model promotion must reject changes that fail out-of-sample
calibration/returns comparisons. Retraining does not guarantee improvement.

## Operational restrictions

The implementation is read-only and has no trade execution or exchange
credentials. Keep Google Drive archiving disabled pending its own OAuth
validation; no new secrets, startup bypasses, or silent changes to the
currently working sports app.

## Point-in-time feature and shadow online learning (next slice)

`perpetuals/features.py` reads the existing immutable per-venue candles,
checks consistent UTC bar intervals and that every candle was **observed**
before the issued prediction, then builds return, volatility, intrabar-range
and relative-volume features. Raw prices from USD and USDC contracts are
never averaged together. It skips simultaneous first-observation timestamps
from historical backfills: a fetched dataset does not prove that a prediction
could have been issued at those old timestamps.

`perpetuals/learning.py` supplies a small online logistic baseline, run in
strict chronological (prequential) order. Each prediction is recorded in
memory **before** feedback, and weights update only when earlier labels have
actually matured. It measures Brier score against a rolling base-rate
benchmark. A favorable result is only a **shadow candidate**; it does not
promote or deploy models automatically. Source-level, cross-venue signals,
calibration and statistically stronger challengers remain future work.

After several days of actual sampled market data are present in production
PostgreSQL, run the **read-only** evaluation (no model publication):

    python -m parlay_bot.perpetuals.evaluate --provider dydx --asset BTC --interval 5 --horizon 15

Or use `--provider hyperliquid`. If only one-shot backfills exist, the
correct output is zero causal examples, not made-up historical live accuracy.
There is no live trading, periodic training or automatic promotion in this slice.

## October 28: Automatic data collection ON after production deployment

RivaL's Discord process starts its read-only perpetual market-data worker
**automatically** whenever the existing runtime is using PostgreSQL.
No manual shell command, Kraken account, API key, per-user trigger, external
cron, or Discord interaction is needed to collect.

The first supported sources are Hyperliquid (USDC perp contracts) and dYdX
v4 (USD perp contracts). BTC, ETH and SOL run immediately after the Discord
Gateway becomes ready, followed by one bounded cycle every 300 seconds.
The default fetch window is 48 completed five-minute candles per asset.
Replayed history is idempotent and cannot silently overwrite changed candles.
First-observed timestamps are preserved for time-safe future evaluation.

If a source is blocked, rate-limited, temporarily unavailable or sends invalid
data, the other source/assets continue. The collector remembers a cooldown
for explicit 403/451/401 regional/access blocks (six hours) and HTTP 429
(twenty minutes). It does not bypass restrictions or retry rapidly.
Failures and successful inserts are stored in the separate `perp_feed_health`
table and logged without secrets; they never take down Discord.

Use the new private Discord command **`/rival-data`** to see the actual
last successful collection and number of newly stored candles per source.
Logs include:

    RivaL perp automatic collector ENABLED venues=hyperliquid,dydx ...
    RivaL perp automatic collector RUNNING
    RivaL perp collection OK venue=hyperliquid asset=BTC bars=48 new=48

If you see FAILED status or no new candles, the source is not collecting
successfully. **A green GitHub Actions run does NOT prove the process is
deployed or that Discloud can access the exchange.** Check Discloud after
upload/redeploy. This has no effect on sports-only `/rival` command.

Configuration is optional and defaults to ON on PostgreSQL:

    RIVAL_PERP_COLLECTION_ENABLED=true
    RIVAL_PERP_COLLECTION_ASSETS=BTC,ETH,SOL
    RIVAL_PERP_COLLECTION_SECONDS=300
    RIVAL_PERP_COLLECTION_BARS=48

Set RIVAL_PERP_COLLECTION_ENABLED=false to temporarily stop it.
SQLite local/test deployments do not start it. A new revision must be
deployed to Discloud before any data starts flowing, and the older overnight
hours were NOT previously captured as live observations. Initial historic
candles are marked as backfill by first_observed timestamp.

This only **collects** data; automated forecasting/model retraining and
production accuracy validation remain incomplete and cannot be inferred from
successful candle writes.

## Additional perpetual feed candidates and status formatting fix

Bitget Futures is a public no-key USDT perpetual candle provider with official
`GET /api/v3/market/instruments` and `GET /api/v3/market/candles`
endpoints. Verify type=perpetual/status=online and use only
`category=USDT-FUTURES` on each BTCUSDT/ETHUSDT/SOLUSDT contract.

Gate V4 futures is a different USDT contract feed. Verify direct, active
BTC_USDT/ETH_USDT/SOL_USDT contracts with
`GET /api/v4/futures/usdt/contracts/{contract}`, then collect bounded
`GET /api/v4/futures/usdt/candlesticks` responses. Gate reports volumes in
contract units. Use the current direct-contract `quanto_multiplier` only after
validation to produce base-asset volumes. Contract metadata changes can trigger
immutable-history conflicts and must not silently rewrite old data.

Official documentation:
- https://www.bitget.com/docs/catalog/market/market-data
- https://www.gate.com/docs/developers/apiv4/en/futures/

Neither API's successful response is proven from Discloud yet. HTTP 401/403/451
blocks and rate limits must fail closed, remain visible and enter the existing
cooldown, never be bypassed. Candle prices/contract identities are venue-specific
and must not be merged as if interchangeable. A missing per-bar trade count is
written as sentinel `-1` (unknown), NOT `0` trades. Never feed that sentinel
to a learned trade-count feature.

The private `/rival-data` response now uses actual newline rendering, shows
the number of latest successful venues of the *configured* source list and the
separate ten-source target. Historical initial 48-bar backfill is not evidence
that the bot observed 48 consecutive live intervals.

Production activation requires deploying the newer main commit to the existing
Discloud RivaL app and checking actual status rows. GitHub CI is not a runtime
feed audit.

## The new interactive /rival-data dashboard

The command is now a private multi-screen menu, **not** a long embed with an
entry for each exchange/coin combination.

- **Overview**: live/configured venues, fresh-market pairs, total persisted
  candles, last successful sync and progress against ten-source target.
- **Exchanges**: use the dropdown to inspect one exchange at a time. BTC, ETH
  and SOL show accurate status, last success and cumulative inserted candles.
- **Markets**: use the dropdown to choose an asset, then inspect the most recent
  *stored* five-minute candle for each venue separately. USD, USDC and USDT are
  explicitly labeled rather than averaged into a misleading price.
- **Refresh**: re-fetch live status from the existing PostgreSQL market store
  without generating unnecessary exchange API calls.

A last success is treated as fresh only when the source status is `ok`
and the timestamp is no older than three configured collection intervals.
Stale, failed or never-attempted sources are not counted as active. Controls
are private to the invoking Discord user, expire after 15 minutes, and use
ephemeral interaction responses. Database lookup errors are handled without
exposing secrets. The sports command and existing collection loop are not
changed by this UI-only improvement.

Deploy the newest RivaL main revision to the **existing** Discloud app to see
the interface. A GitHub merge alone does not update Discord.

## OKX and KuCoin public perpetual market adapters

**New code integrations, not yet verified active from Discloud.** RivaL checks
OKX V5 `public/instruments?instType=SWAP&instId=...` metadata and only
collects live, linear, USDT-settled SWAP contracts from `market/candles`.
For a linear contract with `ctValCcy` equal to the coin, base volume equals
exchange contract-count `vol` times `ctVal` and `ctMult`. The adapter
honors OKX's completed-candle confirm flag.

For KuCoin, RivaL checks the public futures contract specification via
`api-futures.kucoin.com/api/v1/contracts/{symbol}` and fetches bounded
trade klines from `api.kucoin.com/api/ua/v2/market/kline` with
`tradeType=FUTURES`. Futures volume is the number of contracts; RivaL uses
the public `multiplier` as coin quantity per contract. BTC on KuCoin is
`XBTUSDTM`, NOT BTCUSDTM. Neither source supplies fabricated market
contexts or trade counts, and no account/key/trading permission is needed.

Official reference documentation:
- https://www.okx.com/docs-v5/en/
- https://www.kucoin.com/docs-new/v2/rest/ua/get-klines
- https://www.kucoin.com/docs-new/rest/futures-trading/market-data/get-symbol

The bounded five-minute collector, blocked-source cooldowns, private menu
and existing four venues remain intact. Check `/rival-data` after deploying
the merged revision to determine whether actual Discloud API access,
market identity checks and immutable PostgreSQL inserts succeeded.

The target remains ten independent **verified** venues and outcome-evaluated
forecasts. No model-accuracy claim follows merely from a newly coded adapter.

## Deribit and Binance Futures

RivaL now has two more **coded**, independently labeled no-key exchange
integrations. These remain unverified from Discloud until the operator
deploys the newest `main` and checks the real database-backed status.

- Deribit: only active, linear, USDC-settled
  `BTC_USDC-PERPETUAL`, `ETH_USDC-PERPETUAL`,
  `SOL_USDC-PERPETUAL` (or other supported named perps).
  Read-only `/public/get_instrument` checks instrument type and
  `/public/get_tradingview_chart_data` supplies aligned OHLCV
  with base-currency volume, each with a UTC first-observed timestamp.
- Binance USD-M: only `PERPETUAL` `TRADING` USDT-margined
  contracts validated by public `/fapi/v1/exchangeInfo`, then
  read-only `/fapi/v1/klines`. Volume is in base asset and trade
  count is the actual exchange-reported count. No spot or delivery
  futures are mixed into the observations.

Official docs: https://www.deribit.com/api_console/ and
https://developers.binance.info/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data .

Do not bypass HTTP 401/403/451 regional denial. The existing collector
records the failure and pauses that venue. No exchange credentials are
needed, and 8 coded feeds do not mean 8 healthy feeds. Model retraining
and validated production predictions remain separate from collection.

## Final public-data candidate integrations: Lighter and Phemex

The last two sources bring RivaL to **ten coded candidates**, NOT ten
live-verified venues. The bot only counts fresh successful sources, and
region-blocked/broken venues are excluded, never silently substituted.

Lighter exposes public `GET /api/v1/orderBooks` for perpetual identity,
then `GET /api/v1/candles` (bounded market_id/resolution/time window).
Its request bounds are Unix seconds but candle `t` uses milliseconds;
lowercase `v` is base-volume. Market identifiers come from the active
perpetual listing, not a hardcoded assumption about BTC/ETH/SOL market IDs.
This adapter calls only public REST and does not attempt to access a
geographically restricted websocket stream.
Documentation: https://github.com/elliottech/lighter-python/blob/main/docs/CandlestickApi.md .

Phemex V2 USDT perpetuals are selected from the public
`GET /public/products` `perpProductsV2` list with Listed status,
then collected using
`GET /exchange/public/md/v2/kline/last`. Kline array positions
represent seconds timestamp, seconds interval, prior close, actual OHLC,
**base-asset** volume, quote turnover. No inverse contracts or spot.
Documentation:
https://github.com/phemex/phemex-api-docs/blob/master/Public-Hedged-Perpetual-API.md .

Deployed data still needs successful automatic collection checks for
OKX, KuCoin, Deribit, Binance, Lighter and Phemex. A successful CI run
validates the tested parser contracts, not live access from Discloud.
When data is flowing, the next development priority is point-in-time
features, a calibrated multi-source forecast, delayed-outcome settlement
and controlled automated retraining, not simply more collection widgets.

## Ten-provider mobile Data Center pagination

The Markets screen shows **at most four exchanges on one page**, even when
all ten candidate sources are configured. Previous/Next buttons navigate
pages 1/3, 2/3 and 3/3 in the existing ephemeral menu. Buttons disable at
the ends and the page resets when reentering Markets. The selector for
BTC/ETH/SOL remains. Each page reads only its visible exchanges' latest
five-minute candles, avoiding a wall of ten source fields and unnecessary
database reads. This does not change the collection loop or trained model.

## Source Coverage and prediction-track transparency

The private /rival-data menu has a **Coverage** tab. It reports the actual
Discloud host's status for each BTC/ETH/SOL venue and lists only other
currently healthy, recently synced exchanges as *available market-data
alternatives*. This is **not a prediction fallback**; source-weighted
forecasting and Gemini are not yet deployed.

A provider HTTP 401/403/451 means only that the deployment was denied.
It **does not establish which country is restricted**, whether a Discord
user can trade there, or why the provider denied access. Source limits,
timeouts, unavailable instruments and invalid candles are separate
statuses. RivaL does not bypass these restrictions.

The Overview now distinguishes live collection from learning explicitly:
the deterministic learner remains shadow research, and Gemini is not
yet wired into automatic analysis. No provider credential or rate
limit changes are made by this UI.
