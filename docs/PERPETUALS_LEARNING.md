# RivaL multi-venue forecast/learning core

**Status: foundational domain layer, not a live perpetuals prediction bot.**
The existing Discord sports interface and deployment are intentionally unchanged.
This uses the existing PostgreSQL connection via `RelationalHotStore` when
initialized, and only adds isolated `perp_predictions` and `perp_source_skill`
tables. The ledger is not yet wired into runtime startup.

## Ten source candidates

Hyperliquid, dYdX, Lighter, Deribit, Binance Futures, OKX, Bitget, Gate
Futures, KuCoin Futures and Phemex. **Kraken is excluded.** All candidates
require confirmation of public read-only access, regional eligibility, symbol
and contract semantics, rate limits and uptime from Discloud before enabling.
See GitHub issue #6 for each venue's official documentation and constraints.

## Source fusion

`SourceForecast` requires a venue-specific, point-in-time **forecast
probability** generated by a separately validated upstream prediction model.
A raw price, agreement statistic, or funding rate is *not* a probability.
`fuse_forecasts` refuses instrument/horizon mismatches, rejects future/stale
or low-quality observations, deduplicates mirrored upstreams, requires at
least three independent source origins, caps any venue at 40%, and shifts
disagreeing forecasts toward 50%. It never fabricates unavailable observations
or averages prices across venues. The resulting agreement is **not** measured
prediction accuracy, and no claim of predictive edge is made here.

## Delayed learning

`PredictionLedger` saves predictions and all contributing probabilities
immutably, using the same relational store as RivaL's production application.
It is safe to retry record/settle without double-counting. Settlement
requires a real market observation from the original reference venue,
timestamped at the forecast's due time within two minutes. Until then,
the prediction cannot update source skill. Each settled outcome updates a
per-asset, quote, horizon and upstream-origin Brier score, including a
discounted recent score. Subsequent fusions favor better historical scorers.
`performance()` reports results only from settled observations.

This is **online reliability-weight adaptation**, not autonomous model
training. To implement the requested continually learning system, RivaL
still needs: 10 permitted live adapters, historical backfill, normalization,
features, leakage-proof labeling, model training/calibration, proper
walk-forward tests, controlled challenger/champion promotion, scheduled
outcome settlement, source-health gating, Discord presentation and Discloud
validation. Model promotion must reject changes that fail out-of-sample
calibration/returns comparisons. Retraining does not guarantee improvement.

## Operational restrictions

The implementation is read-only and has no trade execution or exchange
credentials. Keep Google Drive archiving disabled pending its own OAuth
validation; no new secrets, startup bypasses, or silent changes to the
currently working sports app.

## Point-in-time feature and shadow online learning (next slice)

`perpetuals/features.py` reads the existing immutable per-venue candles,
checks consistent UTC bar intervals and that every candle was **observed**
before the issued prediction, then builds return, volatility, intrabar-range
and relative-volume features. Raw prices from USD and USDC contracts are
never averaged together. It skips simultaneous first-observation timestamps
from historical backfills: a fetched dataset does not prove that a prediction
could have been issued at those old timestamps.

`perpetuals/learning.py` supplies a small online logistic baseline, run in
strict chronological (prequential) order. Each prediction is recorded in
memory **before** feedback, and weights update only when earlier labels have
actually matured. It measures Brier score against a rolling base-rate
benchmark. A favorable result is only a **shadow candidate**; it does not
promote or deploy models automatically. Source-level, cross-venue signals,
calibration and statistically stronger challengers remain future work.

After several days of actual sampled market data are present in production
PostgreSQL, run the **read-only** evaluation (no model publication):

    python -m parlay_bot.perpetuals.evaluate --provider dydx --asset BTC --interval 5 --horizon 15

Or use `--provider hyperliquid`. If only one-shot backfills exist, the
correct output is zero causal examples, not made-up historical live accuracy.
There is no live trading, periodic training or automatic promotion in this slice.

## October 28: Automatic data collection ON after production deployment

RivaL's Discord process starts its read-only perpetual market-data worker
**automatically** whenever the existing runtime is using PostgreSQL.
No manual shell command, Kraken account, API key, per-user trigger, external
cron, or Discord interaction is needed to collect.

The first supported sources are Hyperliquid (USDC perp contracts) and dYdX
v4 (USD perp contracts). BTC, ETH and SOL run immediately after the Discord
Gateway becomes ready, followed by one bounded cycle every 300 seconds.
The default fetch window is 48 completed five-minute candles per asset.
Replayed history is idempotent and cannot silently overwrite changed candles.
First-observed timestamps are preserved for time-safe future evaluation.

If a source is blocked, rate-limited, temporarily unavailable or sends invalid
data, the other source/assets continue. The collector remembers a cooldown
for explicit 403/451/401 regional/access blocks (six hours) and HTTP 429
(twenty minutes). It does not bypass restrictions or retry rapidly.
Failures and successful inserts are stored in the separate `perp_feed_health`
table and logged without secrets; they never take down Discord.

Use the new private Discord command **`/rival-data`** to see the actual
last successful collection and number of newly stored candles per source.
Logs include:

    RivaL perp automatic collector ENABLED venues=hyperliquid,dydx ...
    RivaL perp automatic collector RUNNING
    RivaL perp collection OK venue=hyperliquid asset=BTC bars=48 new=48

If you see FAILED status or no new candles, the source is not collecting
successfully. **A green GitHub Actions run does NOT prove the process is
deployed or that Discloud can access the exchange.** Check Discloud after
upload/redeploy. This has no effect on sports-only `/rival` command.

Configuration is optional and defaults to ON on PostgreSQL:

    RIVAL_PERP_COLLECTION_ENABLED=true
    RIVAL_PERP_COLLECTION_ASSETS=BTC,ETH,SOL
    RIVAL_PERP_COLLECTION_SECONDS=300
    RIVAL_PERP_COLLECTION_BARS=48

Set RIVAL_PERP_COLLECTION_ENABLED=false to temporarily stop it.
SQLite local/test deployments do not start it. A new revision must be
deployed to Discloud before any data starts flowing, and the older overnight
hours were NOT previously captured as live observations. Initial historic
candles are marked as backfill by first_observed timestamp.

This only **collects** data; automated forecasting/model retraining and
production accuracy validation remain incomplete and cannot be inferred from
successful candle writes.

## Two independent research tracks and restart-safe AI caching

**/rival-research** is a private Discord menu with Math & History and
Gemini AI pages. BTC/ETH/SOL can be selected without exposing credentials.

- **Math & History** audits actual PostgreSQL candle counts over the preceding
  six calendar months for each configured source/asset, labeling the ratio
  as an *upper bound* until gaps, corrections and availability are audited.
  Existing statistical training is still shadow-only: no calibrated real-money
  bet is produced. Historical backfills are **not** live observations.
- **Gemini AI** is an explicitly triggered second track, never automatically
  substituted for the mathematical model. It reads every currently healthy
  exchange with recent closed candles and computes per-venue 15m/1h/4h/24h
  returns/volatility, plus any present 7d/30d/90d/6-calendar-month baseline
  returns. Bad, stale and region-blocked sources are excluded and disclosed.
  It does not average different USDC/USD/USDT markets as exact equivalents.
- Gemini returns a separate qualitative 15m direction and uncalibrated
  confidence and risks. This has **no verified edge**, cannot trade, and
  does not modify math-model weights. Model evaluation, actual settlement,
  calibration and model promotion are still future work.

**Smart caching:** The normalized verified evidence has a SHA-256 fingerprint.
An identical evidence/model/asset query serves the saved immutable response
from PostgreSQL even across Discloud restarts, using **zero** Gemini requests.
New closed candles update the fingerprint and are eligible for new analysis,
but global model-wide cooldown is 900 seconds by default, with an atomic
24-request-per-UTC-day limit. A Gemini 401/403/429 triggers a persisted
one-hour circuit breaker. Source polling continues unaffected. The cached
analysis is never served if fresh source validation fails; no stale data
or failed provider is implicitly treated as a working replacement.

Discloud may already have `GEMINI_API_KEY` or `GOOGLE_API_KEY` configured.
RivaL reads one of those environment secrets but never prints or uploads
their values. Optional `RIVAL_GEMINI_MODEL`,
`RIVAL_GEMINI_DAILY_MAX`, and `RIVAL_GEMINI_COOLDOWN_SECONDS`
adjust usage. The model name is configurable because provider model
availability and project quotas change.

Six-month collection and historical backfill are **not implemented in this
slice**; this slice accurately measures missing data and uses the history
that is genuinely present. Full-six-month fetches require venue-specific
retention limits, checksum/gap validation, and host-level availability checks.

## Five-minute perpetuals as the primary research horizon

The owner's primary trading horizon is **5 minutes**. Do not confuse
the existing **five-minute OHLCV sampling interval** with a 15-minute
future forecast. RivaL's Gemini evidence now requests a *next 5m*
qualitative assessment, using observed 5m, 15m, 1h, 4h and 24h
within-venue percentage returns and volatilities, plus any genuinely
stored multi-month baseline observations.

The private Math & History menu shows the **previous completed five-minute
market move** aggregated as a median of independent quoted-venue returns,
with agreement counts and 15m/1h trend context. This is a description
of what happened, *not* a probability that the next candle will have
the same direction. It excludes source data more than seven minutes
old, requiring three distinct fresh exchanges.

The existing scheduled online shadow learner already evaluates both
five-minute and fifteen-minute causal outcomes. It cannot be marketed
as an approved trading model simply because it is running. The future
target planner must use the actual user's asset and chosen timeframe,
expected path volatility, venue-specific quote/spread, fees, funding,
slippage, and a tested target-hit distribution. Accepting a user's
custom profit target must trigger a recalculation rather than blindly
retaining the default probability. Until that is validated, the menu
must show **NO VERIFIED TARGET / NO VERIFIED BET**, not an invented
price or confidence.

## Autonomous math, Gemini, and prediction-accuracy audit (one combined PR)

RivaL's five-minute Discloud collector is the authoritative market clock.
After collection it runs an isolated mathematical prospective-audit cycle:
train from strictly older **resolved labels only**, issue immutable
5m/15m predictions before the respective future candle closes, and score
each when the same exchange confirms the next target candle. The weights
are replayed from the observed data, so the model can learn without the
user making bets. Automatic retraining is not a guarantee of improvement.

A second **Gemini research** path operates by default with an existing
Discloud Gemini key. It only attempts once per BTC/ETH/SOL every **four
UTC hours**, at most 18 candidate requests/day (the separate Gemini quota
table retains its default 24/day cap). Every request requires at least three
currently healthy sources and enough point-in-time history; reuse of
unchanged evidence is free through the SHA-256 PostgreSQL answer cache.
A Gemini opinion is stored as a directional/uncertain qualitative result;
it is not converted into a mathematically calibrated probability. An
additional immutable, venue-pinned, five-minute **AI forward ledger**
records when an opinion was issued, what evidence was available, and how
the later same-exchange close actually moved. Neutral moves and
`uncertain` opinions cannot become fabricated winning predictions.
API failures do not interrupt the mathematical loop or collection.

The shadow model-gate compares forward Brier against a base-rate over
**unique** UTC five-minute target windows; correlated exchanges are
averaged into the same window rather than pretending ten confirmations
are ten independent bets. Qualification requires at least 100 distinct
forward-market windows across at least seven different dates and an
average Brier margin of 0.005. Evaluation re-runs as new outcomes mature,
and the shadow qualification can be withdrawn automatically. It does
**not** authorize live trading or turn a research model into proven profit.

The private /rival-research **Accuracy** tab now queries PostgreSQL
each time and separately reports mathematical 5m/15m calibration and
Brier, forward unique-market timestamps, a previous-week comparison
where sufficiently populated, sample/model-gate counts, and Gemini
directional decisions/abstentions. Cost-adjusted sample bps are
**hypothetical** using an assumed 20 basis-point roundtrip cost and
are explicitly not exchange fills; no funding or actual execution data.
Out-of-sample improvement and financial profitability require further
long-run verification, source-gaps review, risk limits and actual venue
execution assumptions. No automatic wager is made.

Set `RIVAL_GEMINI_AUTO_ENABLED=false` to disable the budgeted AI worker
without affecting all mathematical monitoring and data collection.

### Staggered automatic Gemini scheduling

Because RivaL enforces a model-wide 15-minute request cooldown, the
three-coin four-hour UTC analysis round **must not fire three back-to-back
API calls**. The live scheduler now attempts BTC in minute 00–04,
ETH in minute 20–24, and SOL in minute 40–44 of each qualifying four-hour
UTC cycle. Six cycles per day times three assets is at most 18 attempts,
under the 24-request/day local budget. Each asset has its own persisted
four-hour slot and retries cannot multiply requests across restarts.

## Six-month gap audits and first bounded historical recovery

Unlike a count ratio such as "1,085 / 527,040", this audit reads each
stored five-minute candle's **actual UTC opening timestamp** and checks
whether every expected point exists in the preceding **six calendar months**.
A per-venue/coin report includes expected, valid and missing slots, gap
segments, largest gap, malformed timestamps and observations made before
the source candle closed (or after the audit time). Only a window with
zero missing or invalid bars is marked **complete**. The audit is
low-priority, one coin across venues per hour, and reports its *last
completed scan*, not a falsely live audit of half a million rows on each
button press.

RivaL now starts a separate bounded Gate USDT Futures recovery by default
once deployed, performing at most one **600-candle ranged** GET per BTC,
ETH and SOL every five minutes. Gate's public V4 documentation supports
`from`, `to`, `interval=5m` and up to 2,000 bars per request. We
deliberately stay below its maximum. Each request first verifies an active,
direct contract and the published `quanto_multiplier` used to normalize
volume. Valid candles import to the preexisting immutable PostgreSQL
table; the **actual retrieval date** becomes `first_observed_at`.
This makes them useful for historical research but **never** eligible
to masquerade as predictions placed months ago.

The progress table stores per-coin cursor, attempts, imported count,
empty-result windows and provider cooldown. A retry never overwrites or
rewinds older observations. HTTP 401/403/451 cannot be bypassed and
pauses only the historical source for six hours. Collection of the
other nine live sources, automatic shadow evaluations, Gemini budgets
and Discord remain independent. Inspect Math & History to see the
latest verified gap status and Gate recovery cursor/progress.

Documentation:
- https://www.gate.com/docs/developers/apiv4/en/futures/
- https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint

**This is not a claim that six months are already downloaded.**
Recovery takes subsequent scheduled requests, and a provider may lack
older data, have gaps or block host access. Each other venue requires
a separately validated historical adapter or independently acquired
quality-checked data. Historic row counts, source count, and GitHub
tests do not prove positive out-of-sample trading returns, real exchange
fills, user eligibility or permission to trade.
