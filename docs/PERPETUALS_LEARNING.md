# RivaL multi-venue forecast/learning core

**Status: foundational domain layer, not a live perpetuals prediction bot.**
The existing Discord sports interface and deployment are intentionally unchanged.
This uses the existing PostgreSQL connection via `RelationalHotStore` when
initialized, and only adds isolated `perp_predictions` and `perp_source_skill`
tables. The ledger is not yet wired into runtime startup.

## Ten source candidates

Hyperliquid, dYdX, Lighter, Deribit, Binance Futures, OKX, Bitget, Gate
Futures, KuCoin Futures and Phemex. **Kraken is excluded.** All candidates
require confirmation of public read-only access, regional eligibility, symbol
and contract semantics, rate limits and uptime from Discloud before enabling.
See GitHub issue #6 for each venue's official documentation and constraints.

## Source fusion

`SourceForecast` requires a venue-specific, point-in-time **forecast
probability** generated by a separately validated upstream prediction model.
A raw price, agreement statistic, or funding rate is *not* a probability.
`fuse_forecasts` refuses instrument/horizon mismatches, rejects future/stale
or low-quality observations, deduplicates mirrored upstreams, requires at
least three independent source origins, caps any venue at 40%, and shifts
disagreeing forecasts toward 50%. It never fabricates unavailable observations
or averages prices across venues. The resulting agreement is **not** measured
prediction accuracy, and no claim of predictive edge is made here.

## Delayed learning

`PredictionLedger` saves predictions and all contributing probabilities
immutably, using the same relational store as RivaL's production application.
It is safe to retry record/settle without double-counting. Settlement
requires a real market observation from the original reference venue,
timestamped at the forecast's due time within two minutes. Until then,
the prediction cannot update source skill. Each settled outcome updates a
per-asset, quote, horizon and upstream-origin Brier score, including a
discounted recent score. Subsequent fusions favor better historical scorers.
`performance()` reports results only from settled observations.

This is **online reliability-weight adaptation**, not autonomous model
training. To implement the requested continually learning system, RivaL
still needs: 10 permitted live adapters, historical backfill, normalization,
features, leakage-proof labeling, model training/calibration, proper
walk-forward tests, controlled challenger/champion promotion, scheduled
outcome settlement, source-health gating, Discord presentation and Discloud
validation. Model promotion must reject changes that fail out-of-sample
calibration/returns comparisons. Retraining does not guarantee improvement.

## Operational restrictions

The implementation is read-only and has no trade execution or exchange
credentials. Keep Google Drive archiving disabled pending its own OAuth
validation; no new secrets, startup bypasses, or silent changes to the
currently working sports app.

## Point-in-time feature and shadow online learning (next slice)

`perpetuals/features.py` reads the existing immutable per-venue candles,
checks consistent UTC bar intervals and that every candle was **observed**
before the issued prediction, then builds return, volatility, intrabar-range
and relative-volume features. Raw prices from USD and USDC contracts are
never averaged together. It skips simultaneous first-observation timestamps
from historical backfills: a fetched dataset does not prove that a prediction
could have been issued at those old timestamps.

`perpetuals/learning.py` supplies a small online logistic baseline, run in
strict chronological (prequential) order. Each prediction is recorded in
memory **before** feedback, and weights update only when earlier labels have
actually matured. It measures Brier score against a rolling base-rate
benchmark. A favorable result is only a **shadow candidate**; it does not
promote or deploy models automatically. Source-level, cross-venue signals,
calibration and statistically stronger challengers remain future work.

After several days of actual sampled market data are present in production
PostgreSQL, run the **read-only** evaluation (no model publication):

    python -m parlay_bot.perpetuals.evaluate --provider dydx --asset BTC --interval 5 --horizon 15

Or use `--provider hyperliquid`. If only one-shot backfills exist, the
correct output is zero causal examples, not made-up historical live accuracy.
There is no live trading, periodic training or automatic promotion in this slice.
