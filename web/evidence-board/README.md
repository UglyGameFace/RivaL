**Independent public dashboard:** https://evidence.the420lobby.com/ (Cloudflare Worker `rival-evidence-board`). This site is hosted outside ChatGPT; [hosting, dependencies, deployment and recovery](HOSTING.md) document how to preserve it. The existing https://rival.the420lobby.com/ site remains separate.

## Model identities and intermittent production reads

The signed `performance.model` identifies the **incumbent scoring model**, currently `prospective-logistic-persistent-v3`, only when at least one valid signed settled score scope was observed. Model Lab cards, its complete comparison table and drilldowns show this exact version; Signals shows the model version on individual signed forecast rows when available. The model's Brier score is not a claim that the same artifact is currently served in Discloud and not proof of a profitable trading strategy.

The host XMarket shadow counter is explicitly filtered to the `xmarket_v1` family, so the dashboard names that *family* when real shadow rows appear in a verified host receipt. This is not a unique imported model version or an assurance that a candidate is promoted. It remains separate from the incumbent scoring model.

The twelve BTC/ETH/SOL/XRP 5m/15m/60m score scopes share this scored-incumbent identity. Imported XMarket artifact identities are now joined per scope when the host receipt publishes them: a 12-hex digest prefix (recomputed from the Drive document's canonical JSON and matched against the host import record), `trained_through`, and serving status (imported / enabled / serving / shadow-only / rejected). The full digest, Drive file ID, and weights never leave the host. The UI explicitly distinguishes challenger imports/issuance from incumbent paired scoring; no fallback invents a challenger ID, an artifact hash, or a trading edge.

A GitHub-signed receipt can be fresh while its Discloud or PostgreSQL read failed. The home page now flags the **current signed host/database read error** and, if available, shows the most recent historically verified host/database counters from the existing signed metrics series, with their own timestamp and a visible **not live** warning. It refuses history older than 24 hours. Latest-source health stays unverified, even if a prior receipt had issued forecasts. Previously saved signed per-call forecast rows can be shown as dated historical observations if the newest host read fails; no dated row becomes a new live call. All counts and probabilities remain research evidence, not trading execution.

Cloudflare Workers Builds now has a separate **production main-branch push trigger for each Evidence Worker**, with exact source/test watch paths and previews disabled. The Evidence Board's first real GitHub-triggered build and exact-source deployment completed successfully on 2026-11-16 at approximately 04:04:57 UTC. The Collector trigger is configured, but its first successful independent CI/CD deploy must still be observed. Both share the existing Cloudflare-managed deployment token without placing credentials in GitHub. Build and deploy commands are documented in [RIVAL_EVIDENCE_AUTODEPLOY.md](../../docs/RIVAL_EVIDENCE_AUTODEPLOY.md).

## Host-native XMarket scope progress

The production Discloud read-only health receipt already computes twelve `scope_progress` entries covering BTC/ETH/SOL/XRP × 5m/15m/60m. Earlier Evidence Board publication discarded these and only exposed aggregate imports and shadow counts, leaving the XMarket screen unable to identify which scopes were actually issuing. The signed publisher now allows only fixed asset/horizon/status, bounded original source count, imported-artifact count, prospective shadow-row count and last observed timestamps. The separate Cloudflare OIDC receiver independently revalidates and redacts the same fields. It never releases private model documents, raw contract or Drive IDs, feature weights or account information.

**XMarket** now shows host-reported scope states and shadows beside, but never conflated with, historical Drive training reports. A host-side saved artifact is not necessarily the currently serving model identity. If the production host lacks this receipt version, the UI states **not published**, rather than filling the twelve cells from unrelated aggregate totals. Reports can be blocked while an independently older imported artifact still issues research shadows; that is a source chronology distinction, not a contradiction to suppress. The per-scope data remains a dated read-only research observation, not actionable trade calls or proof of after-cost profit.

## Model/forecast completeness (Delivery 2, November 17, 2026)

The signed receipt now also carries `host.model_artifacts` (incumbent family/version, serving status, lineage digest prefixes, Model Lab state, and imported XMarket artifacts), `host.paper_proof` (exact-source paper evaluation: best exact source with its five gate checks, per-scope aggregates, and scope handoff counts), `host.research_loop` (Model Lab experiments by status), `host.xmarket_quotes` (per fitted scope, per venue entry/closed/missed quote rows), and `host.xmarket_watchdog` (issuance health per scope). Drive reports now carry a 12-hex artifact digest prefix and up to four short gate failures. The Signals view shows up to three recent forecasts per scope (36 rows max, 6h window) with target-open/settled timestamps, outcome and next-target readiness filters, and pagination; the Models view shows artifact identity and the Lab; the XMarket view shows per-scope paper evaluation, quote availability, and watchdog status.

Two honest bounds. First, the signed receipt must stay under the collector's **80KB cap**: paper proof is aggregated per scope instead of per venue (71 source evaluations become up to 12 scope rows), and forecast history is bounded at three per scope. Delivery 4 measured the combined D1+D2+D3 receipt and found the pre-budget worst case at 106,820 bytes (live-like 82,629 bytes) — over the cap, so a worst-case run would have been rejected with 413 and lost that publication. The Delivery 4 budget (20 RivaL PRs including every pinned PR, 12 runs; 8 Intelligence PRs/runs; 80-char gate failures) brings the worst case to 73,212 bytes with 6,788 bytes of headroom, enforced by `test_worst_case_combined_receipt_fits_with_headroom` in `tests/test_evidence_board_receipt.py`. A full forecast ledger or per-venue paper table needs a separate history endpoint, not a bigger receipt. Second, **observed fees, spread, slippage, funding, and stressed after-cost results are not published by the host receipt** — paper cost evidence uses assumed fees and real fills are not verified; the board says so rather than implying execution. Zero after-cost qualified models remains the truthful result: qualification still requires ≥150 independent forward outcomes, 21 days, 80% matched quote coverage, baseline improvement, and positive stressed performance after realistic costs.
## Authenticated LFM3 metrics receipt (Delivery 3)

The publisher (`tools/evidence_board_receipt.py`) runs one read-only console command inside the LFM3 container. That command reads the port and bearer token from the container's own environment, calls its authenticated `GET /v1/status`, and prints only a bounded `RIVAL_LLM_METRICS_RECEIPT=` marker with model, readiness, source SHA, repair state/count, runtime context tokens, the cgroup memory snapshot and the status-request latency. The same program then issues one real authenticated `/v1/research` generation with the synthetic read-only body and, when the response is the safely-grounded shape, adds `inference_verified`, the `authenticated_generation` probe marker, generation latency and tokens/second to the marker. The publisher never holds the LFM3 token and never logs console output. The collector (`web/evidence-board/collector.js`) revalidates the same allowlist before signing it into the receipt as `intelligence_metrics`. Until the deployed host emits the marker, every metric is `unavailable`, never a fabricated healthy value. `/v1/status` proves authenticated backend readiness only: `inference_verified` stays false unless the host-side authenticated generation probe emits it. Generation latency and tokens per second are now emitted by the host probe; CPU, DNS/upstream and database-pressure fields exist in the schema but stay null (no host probe measures them yet). `GET /api/status` now also reports `intelligence_metrics_status` and `intelligence_inference_verified` as a separate dimension that does not gate overall health.

## Market prediction linkage and history retention (Delivery 3)

`/api/market/predictions` now carries, per Polymarket contract, the market-implied Up probability (mid of the carried Up bid/ask, null when a side is missing), a `quote_state` (`observed`, `expired`, `not_accepting_orders`, `missing_side`), a `usable` flag, and explicit nulls for `resolution_rule` and `settlement` with source `not_carried_by_feed`. Per Kalshi market it carries the summary-implied YES probability with `quote_kind: market_summary_not_executable` and `executable: false`. DraftKings Predictions is returned as `status: disconnected` with reason `no_authorized_verified_source` and no quotes. `/api/market/perps` now exposes per-venue `quote_age_ms` (the upstream field is named `latency_ms` but holds the quote's age at the source; the old code read a nonexistent `age_ms` field and always returned null) and `quote_kind` (`indicative` vs `receipt_backed`).

The collector's `metrics-series` keeps the last 72 signed receipts (about a day at the 10-minute cadence) with a `schema_version` per point, bounded per-point Drive counts (accepted/rejected/blocked/fitted) and a compact LLM summary; full per-run receipts live 90 days under `run:<id>` but are not aggregated. The Diagnostics Trends tab therefore cannot show trends longer than about a day, and says so. Per-venue matched entry/exit paper coverage is not in the signed receipt, so no exchange is individually credited with paper evidence; the Markets page states the qualified-vs-evaluated paper-scope totals instead.

## Evidence integrity acceptance

The Command screen includes a **source-by-source integrity panel**, rather than treating a recent GitHub-signed receipt as an overall green light. It separately reports receipt freshness, Discloud forecast/learning freshness, PostgreSQL read success, private Drive report verification, public market quote freshness and LFM3 authenticated inference status. Missing or delayed evidence remains visibly unverified; site liveness, code deployment, forecast quantity, model artifact identity and after-cost qualification are not interchangeable.

The read-only `GET /api/status` endpoint now returns `data_health: checked | partial | delayed_or_unverified | unavailable`, `evidence_recent`, and individual host/database/forecast/learning/Drive flags. HTTP 200 means the latest signed receipt is recent **and** the host, database and forecasting/learning read checks passed. HTTP 503 means the production evidence was partially unavailable, stale, unverified or unreachable, even when the HTML Worker itself is serving. Neither response constitutes a profit claim. Browser refresh errors invalidate the current-health badge while leaving any earlier dated observation available for inspection.

Regressions: `node tools/test_evidence_board_status.js`, `node tools/test_evidence_board_ui.js`, and `python -m unittest tests.test_evidence_board_ui_source`. The status tests simulate healthy, host-failed, DB-failed, stale, future-dated, unsigned and collector-down inputs. Before calling a release accepted, compare live Worker source with merged GitHub bytes, verify bindings and the custom domain, check the deployed `/api/status` response and validate mobile and desktop rendering. GitHub CI and Cloudflare deployment success alone do not verify those HTTP/browser outcomes.

## Two independently timestamped read-only data pipelines

1. **Signed production evidence**: GitHub Actions `.github/workflows/evidence-board-receipt.yml` collects bounded authenticated Discloud, PostgreSQL, private Drive and Intelligence observations, obtains short-lived GitHub OIDC identity, and publishes to the separate Cloudflare `rival-evidence-collector` Worker with signature/issuer/repository/main/ref/event validation. The collector retains only allowlisted sanitized data in KV. Website refresh checks the saved receipt at most once a minute. GitHub cron is best-effort; a successful main push, successful same-repository Production Release, or successful independent hourly Discloud uptime run can trigger additional publication. Each event uses the evidence workflow's own OIDC signature and source reads. Every health claim must include the capture time and source age.
2. **Public market quotes**: the dashboard Worker binds `RIVAL_MARKET_FEED` as a Cloudflare service binding to the already deployed `rival-public-site` Worker. Only `GET /api/perps`, `GET /api/polymarket?asset=BTC|ETH|SOL|XRP`, and `GET /api/kalshi?asset=BTC|ETH|SOL|XRP` are invoked. They are exposed by the dashboard under `/api/market/perps` and `/api/market/predictions?asset=...`, respectively. The server uses an explicit per-field allowlist; strips token IDs, cookies, all private data, unexpected fields and unrecognized assets; and never forwards caller headers or arbitrary URLs. Each upstream has an independent result, unknown values remain `null`, bad sources fail closed or return partial read-only results. Public quotes update about every 30 seconds while the page is visible and are labeled separately from Discloud evidence. Source worker-side market caches avoid repeated exchange fan-out on every page paint.

The dashboard never sends an order, stores credentials in its public script, issues a model prediction, initializes production tables, trains a model, publishes to private Drive, writes Discloud data or changes model promotion rules. The public site itself has trading disabled.

## Signed recent forecast data path

The production Discloud worker's existing \`parlay_bot.perpetuals.learning_health_receipt.read_receipt\` includes a bounded \`recent_forward_calls\` field from \`dashboard_forward_receipt.read_forward_calls\`, **without** training, running inference or mutating the database. It reads the latest persisted incumbent rows from the existing \`perp_forward_audit\` table using one indexed \`SELECT … ORDER BY issued_at DESC LIMIT 3\` per supported asset/horizon (36 rows maximum across twelve scopes). A row is admitted only when it was issued before the actual five-minute target-candle close and has finite probabilities in [0,1]. Settled outcomes are only identified when the settlement clock follows the target close, never inferred or fabricated.

The GitHub-hosted publisher re-sanitizes exactly \`asset\`, \`horizon\`, \`venue\`, \`quote\`, \`issued_at\`, \`target_opened_at\`, \`target_close_at\`, \`settled_at\`, \`probability_up\`, \`baseline_up\`, \`direction\`, \`status\`, \`lead_seconds\`, \`outcome_up\`; the **fixed model_version label** is a receipt-wide constant the independent Cloudflare collector re-attaches so rows do not repeat it. The collector verifies OIDC and repeats allowlist/range/timestamp checks before signing and saving the snapshot. No contract IDs, weights, feature hashes, model secrets, broker account IDs, trade orders, raw user data, or Discloud credentials appear in the public receipt. Missing source stays \`read_unavailable\` and a genuinely empty recent table is \`no_recent_forecasts\`; neither is presented as zero model activity overall.

Both **Command** and **Signals** display the recent research forecasts, with actual original issuance and target timestamps, per-call model and baseline UP probabilities, direction, and real settlement state where independently recorded. A model probability above 50% only means the model forecast UP; **it is not a profitable edge threshold or an invitation to place a bet**. A completed/settled row is not promoted into a winning trade. As these are signed snapshots collected best-effort every ten minutes, they cannot be described as streaming or necessarily current.

Implementation validation: \`tests/test_dashboard_forward_receipt.py\` covers causality, settlement clocks, unknowns and read-only indexed queries; \`tests/test_evidence_board_receipt.py\` checks the independent publisher sanitizer; \`tools/test_evidence_collector.js\` tests OIDC acceptance and receiver redaction, including malicious extra fields; and \`tools/test_evidence_board_ui.js\` ensures missing and valid forecasts display differently.

Deployment dependency: the updated \`learning_health_receipt\` must actually deploy to Discloud and the new signed receipt must be captured through the exact matching main publisher and deployed Cloudflare collector. A merged PR, a successful static test or a source cache freshness badge alone does not verify that production emitted \`recent_forward_calls\`.

## Collection reliability runbook (Delivery 1, 2026-11-17)

- Diagnosis: GitHub cron delivered 15 of ~594 scheduled runs in 99h (median gap ~6h; evidence in `tests/fixtures/evidence_board_run_timing_20261117.json`). The dashboard stays green through `workflow_run`/`push` fallbacks, so a green `/api/status` does not prove the schedule works — check Diagnostics → Collection reliability for the last scheduled attempt.
- What to watch: `/api/status` now carries `collection` (last scheduled attempt, last successful signed publication, last attempt outcome/reason), per-source `sources` (status, reason, last success/error, freshness bar), `alerts`, `bindings`, and `incidents`. `/api/diagnostics` adds the market-feed probe and the attempt history. - Failure reasons: a failed publish reports a signed attempt (`failed`, fixed label only) to the collector; a failed run never overwrites the last good snapshot. If the OIDC mint itself fails, no signed attempt is possible and the reason stays in the GitHub run log only.
- Flood guard: `workflow_run`/`push` triggers coalesce onto a receipt younger than 5 minutes instead of re-hitting Discloud/Drive/the receiver. Schedule runs always collect.
- Scheduler patch: `~/workspace/your_files/evidence-board-scheduler-workflow.patch` (Felix places it by hand) drops the Production Release flood trigger and gives each event its own concurrency lane. It changes no permissions, OIDC, or secrets.
- Optional alert webhook: set the `ALERT_WEBHOOK_URL` environment variable on the dashboard Worker to receive a POST (service, level, alert codes only, no secrets) when the alert level changes to critical, at most once per hour per level. Delivery is not verified from this repo.
